Diseñar y construir un sistema de tracking en tiempo real y navegación para delivery, con calidad de nivel empresarial. Estrategia en dos fases:

Fase 1 · Lanzamiento rápido
Mapbox GL JS + Mapbox Tiles + Mapbox Geocoding
Permite validar el producto sin infraestructura propia. Costo inicial asumible con volumen bajo.

MapLibre + Martin + Valhalla + Photon
Migración progresiva cuando el volumen justifique la inversión en infraestructura propia.

Complejidad de la Feature

Esta no es una integración de API: es construir un sistema completo de geolocalización desde cero. Cada componente tiene desafíos propios y la integración entre ellos multiplica la complejidad.

🔴 Complejidad Client-Side (Mobile)

Filtro de Kalman en dispositivo
Implementar un filtro de Kalman 2D/3D funcional en JavaScript/TypeScript, optimizado para no bloquear el main thread. Requiere entender matemática de estimación y trade-offs entre precisión y rendimiento.
Gestión de ciclo de vida del GPS
Manejar permisos en Android/iOS, background execution limits (Android Doze, iOS background fetch), y diferencias entre react-native-geolocation y plugins nativos. Cada OS tiene comportamientos distintos.
Cola offline con IndexedDB/SQLite
Diseñar un sistema de colas que sobreviva a crashes de app, reconexiones automáticas, y sincronización en lote con resolución de conflictos (orden de llegada, timestamps, duplicados).
Muestreo adaptativo en tiempo real
Ajustar dinámicamente la frecuencia de muestreo según velocidad detectada, nivel de batería y estado de red. Requiere monitoreo constante y heurísticas probadas.

🔴 Complejidad Server-Side

Valhalla: setup y mantenimiento
Descargar datos OSM, construir grafos de routing, mantener actualizaciones semanales. Valhalla consume ~4-8GB RAM y requiere scripts de actualización automatizados. No es un "docker pull y listo".
Martin + PostGIS: pipeline de tiles
Configurar OpenMapTiles schema en PostGIS, importar datos (~50GB para datos globales), configurar Martin con style.json personalizado. La generación de tiles requiere tuning de caché y límites de zoom.
Redis Pub/Sub a escala
Manejar >10K conexiones WebSocket simultáneas, persistencia de estado de suscriptores, reconexión con replay de eventos perdidos. Redis single-instance tiene límites.
Photon: búsqueda y autocompletado
Importar datos OSM, configurar indexing, optimizar queries de autocompletado con typos. Requiere ~2-4GB RAM y tuning de relevancia por región.

🟡 Complejidad de Integración

Map Matching + Renderizado en vivo
La geometría retornada por Valhalla (trace_route) debe integrarse con MapLibre como LineLayer, y el marcador del repartidor debe seguir esa geometría con animación de bearing. Cualquier desincronización entre GPS real y ruta matcheada genera artefactos visuales.
Sincronización multi-cliente
El usuario final y el dashboard deben ver la misma ubicación en tiempo real. Requiere manejar orden de mensajes, latencia variable de red, y estados transitorios (ubicación "stale" vs actual).
Geocoding bidireccional
Forward (dirección → coordenadas) para búsqueda de destinos. Reverse (coordenadas → dirección legible) para mostrar al usuario "estás en [calle]". Ambas requieren consistencia con los datos de Valhalla/OSM.

🟠 Complejidad Operativa

DevOps
Orquestar 5+ servicios (Martin, Valhalla, Photon, Redis, PostGIS) con Docker Compose o K8s. Health checks, restart policies, monitoring.
Datos
OpenMapTiles necesita actualización semanal/mensual. Scripts automatizados para descargar, importar y validar datos nuevos.
Debug
Debug GPS errático en producción es complejo. Se necesitan tools de replay de tracks, logs de ubicación y visualización de datos crudos.

Estrategia de Migración

No todo de golpe. Usamos Mapbox inicialmente para lanzar rápido, y migramos progresivamente al sistema propio cuando el volumen lo justifique.

✅ Por qué Mapbox primero

  • •Zero infraestructura. Sin configurar servidores, sin descargar datos, sin mantener grafos de routing.
  • •Time-to-market rápido. El mapa funciona desde el día 1 con un API key.
  • •Costo asumible al inicio. Con volumen bajo, el pricing de Mapbox es razonable.
  • •Validación de producto. Confirmamos que el tracking en tiempo real genera valor antes de invertir en infra.

🚀 Por qué migrar después

  • •Costo predecible. Cuando escalamos a miles de repartidores, Mapbox se vuelve caro. El sistema propio tiene costo fijo.
  • •Soberanía de datos. Control total sobre estilos, datos y lógica de routing.
  • •Personalización. Estilos específicos para delivery, rutas optimizadas para motos, modos de transporte custom.
  • •Privacidad. La ubicación de repartidores nunca sale de nuestra infraestructura.

Criterio de migración

Volumen de usuarios
>1,000 repartidores activos
Costo mensual Mapbox
> $500 USD/mes
Recursos DevOps
1 persona dedicada 2-3 semanas

Cuando se cumplan estos criterios, se inicia la migración al sistema propio. La arquitectura actual está diseñada para que la transición sea progresiva y de bajo riesgo.

⚠️ Consideraciones Fase 1

Vendor lock-in parcial
El código frontend debe abstraer el provider de mapas para facilitar la migración. Usar interfaces y no dependencias directas de Mapbox.
Costo variable
Monitorear el consumo de tiles y API calls. Mapbox tiene pricing por carga de mapa, no por usuario. Puede crecer exponencialmente.
Limitaciones de personalización
No podemos customizar estilos profundamente ni agregar capas propias hasta la Fase 2.

📋 Plan de Migración

1. Abstraer el mapa
Crear un wrapper MapView que acepte cualquier provider (Mapbox o MapLibre). Cero cambios en el resto del código.
2. Levantar tiles server paralelo
Configurar Martin + PostGIS en paralelo sin romper Fase 1. Validar que los tiles se renderizan correctamente.
3. Configurar Valhalla
Setup de Valhalla con datos de la región de operación. Validar trace_route con datos reales.
4. Cutover progresivo
Migrar primero tiles, luego routing, luego geocoding. Cada componente se migra independientemente.
5. Apagar Mapbox
Una vez que todo funciona en el sistema propio, se cancela la cuenta de Mapbox.
