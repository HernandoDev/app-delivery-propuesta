Alcance técnico

Plataforma de logística multiproveedor compuesta por 4 interfaces (app cliente, app repartidor, panel comercio, backoffice admin) sobre un backend único construido como monolito modular en Python/FastAPI. El sistema gestiona el ciclo completo: onboarding de actores, catálogo, pedidos, tracking geoespacial y administración operativa.

Principios de arquitectura

  • •Monolito modular con DDD. Paquetes por dominio (auth, catálogo, pedidos, geo, notificaciones, comisiones). Evita la sobrecarga operativa de microservicios en etapa temprana y permite extraer un módulo cuando la carga lo justifique.
  • •Parametrización total. Valores de negocio (comisiones, tarifas, límites) residen en base de datos. Cero despliegues para cambios de reglas.
  • •Stack abierto por defecto. Solo se integran servicios externos cuando no existe alternativa técnicamente viable.
  • •Iterativo y verificable. Cada MVP entrega funcionalidad end-to-end desplegable y testeable.

Decisiones técnicas clave

  • •Multi-plataforma desde día 1. React Native con un único codebase para iOS y Android.
  • •Python por expresividad. FastAPI para APIs async tipadas con Pydantic, validación automática y documentación OpenAPI.
  • •PostGIS para geoespacial. Evita soluciones externas para queries de proximidad y polígonos.
  • •Desarrollo lean. Un solo desarrollador full-stack. Git local hasta levantar infraestructura cloud dedicada.

Principios aplicados

  • DDependency Inversion. Los servicios dependen de interfaces (Python Protocol), no de implementaciones concretas. Facilita testeo y reemplazo de infraestructura.
  • SSingle Responsibility por módulo. Cada paquete de dominio (catalog, orders, geo...) es autocontenido con sus propios routers, services, repositories, schemas y tests.
  • IInyección de dependencias. FastAPI Depends() para inyectar DB sessions, current_user y servicios. Cero instanciación manual.
  • CComunicación entre módulos. Sincrónica (llamadas directas) en MVP. Preparamos un EventBus (patrón Observer) para migrar a eventos async cuando sea necesario.

Estrategia de evolución a microservicios

  • ①Módulo "caliente". Cuando un módulo (ej. geo) requiere escala independiente, se identifica por métricas de CPU/latencia.
  • ②Extracción. Se copia el paquete a un nuevo repositorio, se adapta a FastAPI standalone con su propia BD.
  • ③API Gateway. El monolito original pasa a consumir el nuevo servicio vía HTTP/gRPC. El resto del sistema no cambia.
  • ④Event Bus compartido. Para consistencia eventual, se introduce RabbitMQ/NATS entre servicios.

Seguridad

Estrategia de seguridad siguiendo OWASP Top 10 y mejores prácticas.

🔐 Autenticación

  • JWT con dos tokens. Access (15min, en memoria) + Refresh (7 días, httpOnly cookie o secure storage).
  • Refresh rotation. Cada uso de refresh genera uno nuevo y revoca el anterior. Prevención de reutilización.
  • Algoritmo RS256. Clave privada firma, pública verifica. Permite verificación sin contactar al backend.
  • Revocación. Lista negra en Redis para logout activo (futuro).
  • Passwords. bcrypt con cost factor 12, mínimo 8 caracteres + validación zxcvbn.

🔒 Autorización

  • RBAC estricto. Dependencia Depends(require_role("admin")) en cada endpoint protegido.
  • Ownership check. Usuarios solo acceden a sus recursos. Validación en service layer.
  • Permisos granulares. Ej: merchant puede modificar solo su catálogo, no el de otros.
  • Multi-tenant lógico. Filtros automáticos por merchant_id en queries sensibles.

🛡️ Protección de endpoints

  • Rate limiting. Middleware SlowAPI: 60 req/min por IP general, 5 req/min en login, 100 req/min en tracking.
  • CORS whitelist. Solo dominios conocidos en producción, * solo en desarrollo.
  • Validación Pydantic estricta. Rechazo automático de tipos erróneos, XSS, inyecciones.
  • SQL injection. Impossible vía SQLAlchemy ORM. Solo queries raw auditadas manualmente.
  • CSRF. Tokens en endpoints de estado (POST/PATCH/DELETE) vía cookies httpOnly.

📦 Datos sensibles

  • TLS 1.3 obligatorio. HSTS header en producción. Redirect HTTP→HTTPS.
  • Encriptación en reposo. PostgreSQL con TDE a nivel cloud provider.
  • Secrets. Variables de entorno vía pydantic-settings. Nunca hardcodeadas. Rotación periódica.
  • Datos de pago. Nunca almacenamos PAN. Solo reference_id del gateway.
  • PII. Campos como email/teléfono con acceso auditado. Retención GDPR-compliant.

📋 Auditoría

  • Logs estructurados. structlog con JSON, request_id por traza, user_id cuando aplica.
  • Tabla append-only. audit_logs sin UPDATE/DELETE. Trigger de BD garantiza inmutabilidad.
  • Eventos críticos auditados. Firma de contratos, cambios de comisión, suspensiones, reembolsos, cambios de rol.
  • Retención. Logs: 1 año. Datos de tracking: 90 días. Pedidos: 2 años. Contratos: 7 años.

🔍 Testing de seguridad

  • Dependencias. safety + pip-audit en CI para CVEs.
  • SAST. bandit para análisis estático de Python.
  • Secrets. detect-secrets pre-commit hook.
  • DAST. OWASP ZAP contra staging mensualmente.
  • Container scanning. trivy en imágenes Docker.

Decisiones técnicas pendientes

Puntos que requieren definición del equipo de producto/negocio antes de avanzar en la fase correspondiente. La arquitectura ya contempla los mecanismos técnicos para soportar cualquier decisión.

Alcance de carrito (MVP 4)

¿El pedido permite ítems de un solo comercio o multi-comercio? Impacta la lógica de despacho, el modelo de orders y la liquidación.

Opción A: single-comercio (recomendado · más simple) Opción B: multi-comercio (más complejo)

Recomendación técnica: iniciar con single-comercio. El esquema de datos ya soporta evolución sin migraciones.

Proveedor de pasarela de pagos (MVP 4)

Definir proveedor local y método de integración. El adapter pattern permite cambiar sin tocar dominio.

API directa REST SDK oficial Redirect + webhook

Modelo de tarifa de envío (MVP 4)

Fija por zona · calculada por distancia (PostGIS) · dinámica por demanda. Afecta el checkout y la estructura de coverage_zones.

Política de aceptación post-promoción (MVP 5)

¿El cambio de comisión requiere aceptación explícita (recomendado legalmente) o es automático por contrato pre-pactado? Afecta el flujo del CommissionService.

Proveedor de mapas (MVP 2)

OpenStreetMap self-hosted (OpenMapTiles) · Mapbox · Google Maps. Trade-off entre costo y calidad.

Recomendación: Mapbox para MVP (bajo costo, buena calidad) con plan de migración a OSM si escala.

Infraestructura cloud (MVP 6)

Proveedor, región, plan de cómputo y base de datos gestionada vs. autohospedada. Necesario antes de pruebas de carga.

Hetzner (costo bajo) AWS (ecosistema) DigitalOcean (simplicidad) Self-hosted (máximo control)

Evidencia de entrega (MVP 4)

¿Foto obligatoria · firma digital · OTP cliente · combinación? Afecta el flujo del repartidor y el storage.

Fuera del alcance técnico

Decisiones de modelo de negocio (estrategia comercial, pricing al cliente, marketing de adquisición, SLAs comerciales, alianzas) son responsabilidad del equipo de producto/negocio. La arquitectura provee los mecanismos técnicos (motor paramétrico, feature flags, logs de auditoría, APIs extensibles) para que dichas decisiones se implementen sin reescritura de código.
